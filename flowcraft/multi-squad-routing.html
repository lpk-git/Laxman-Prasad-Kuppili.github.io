Multi-Squad Dynamic Channel Routing

Jira Automation Jira Custom Fields Webhook JSON Power Automate Switch / Condition Logic Microsoft Teams

Overview

A single, reusable integration that routes Jira automation notifications to the correct Microsoft Teams channel for each squad — without duplicating flows. Squad identity is read from the incoming payload, and Power Automate's routing logic dispatches the message to the right destination automatically.

The Challenge

Multiple squads each needed automation notifications delivered to their own dedicated Microsoft Teams channel. The straightforward approach — one complete Power Automate flow per squad — would work, but at a cost: every new squad required a new flow to be built, tested, and maintained. Over time, this created:

  • Significant duplication across flows that were nearly identical
  • Increased maintenance burden whenever the message format or logic changed
  • Inconsistency as individual flows drifted from each other over time
  • Higher onboarding effort when adding a new squad to the system

Design Approach

Rather than one flow per squad, the integration is designed as a single shared flow with a routing layer. Jira sends all squad events to one webhook endpoint. Power Automate receives the payload, inspects a squad identifier field, and uses a Switch or Condition block to route the notification to the appropriate Teams channel.

Adding a new squad requires only a new branch in the Switch — not a new flow. The upstream Jira rule and webhook remain unchanged.

Routing Logic

Inside Power Automate, the routing uses a Switch control on the squad identifier field extracted from the JSON payload. Each case maps to a "Post message in a chat or channel" action pointing to the corresponding Teams channel.

// Power Automate — Switch routing (pseudocode) Switch ( triggerBody()?['squadId'] ) Case: "squad-a" → Post to Teams Channel A Case: "squad-b" → Post to Teams Channel B Case: "squad-c" → Post to Teams Channel C Default: → Log unmatched payload // no squad matched

How It Works

  1. 1 Trigger: A Jira Automation rule fires on a configured event — such as an issue being created, transitioned, or assigned.
  2. 2 Enrich Payload: The rule reads the squad identifier from a Jira custom field (e.g. a team label or component field) and includes it in the JSON payload alongside relevant issue context.
  3. 3 Send via Webhook: The JSON payload is sent as an HTTP POST to a single shared Power Automate HTTP trigger endpoint.
  4. 4 Receive & Parse: Power Automate receives and parses the JSON payload, extracting the squad identifier field.
  5. 5 Route: A Switch control evaluates the squad identifier and directs execution to the matching case branch.
  6. 6 Deliver: The matching branch posts the formatted notification to that squad's dedicated Microsoft Teams channel.
  7. 7 Default case: If no matching squad is found, the payload is logged or handled gracefully — preventing silent failures.

Technologies Used

Jira Automation Automation rule engine — triggers on the configured Jira event and builds the outbound payload.
Jira Custom Fields Source of the squad identifier — a team label, component, or custom field that identifies which squad owns the issue.
Webhook Single shared HTTP POST endpoint — all squads' events route through one trigger URL, keeping the Jira side simple.
JSON Payload format — carries issue data and the squad identifier from Jira to Power Automate.
Power Automate Integration and routing engine — receives the webhook, parses the JSON, and applies the Switch routing logic.
Switch / Condition Logic The routing layer inside Power Automate — evaluates the squad identifier and directs the message to the correct Teams channel.
Microsoft Teams Delivery destination — each squad has its own channel where notifications are posted.

Benefits

♻️ No Duplication One flow handles all squads. No repeated logic, no near-identical copies to keep in sync.
🔧 Easy to Maintain Changes to message format or logic need to be made in one place only.
➕ Easy to Scale Adding a new squad means adding one Switch case — the Jira rule and webhook are untouched.
📐 Consistent Output Every squad receives notifications in the same format, from the same underlying logic.

Lessons & Reusability

This pattern is not limited to squad routing. The same design — one webhook, one flow, a Switch on an identifier field — can be reused for:

  • Priority routing — route to different channels based on issue priority (Critical → incident channel, Low → backlog channel)
  • Environment routing — route deployment notifications by environment (Dev / Staging / Production)
  • Issue type routing — route bugs, stories, and tasks to different audiences or channels
  • Cross-tool routing — the same JSON payload could be extended to route to Slack, email, or other platforms by adding branches alongside Teams

The key principle: keep the integration point generic, push the routing decision downstream into the flow where it is cheaper to change.
