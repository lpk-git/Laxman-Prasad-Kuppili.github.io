How to Send GitHub Push Notifications to Communication Channels Using Webhooks

A beginner-friendly journey from a simple GitHub → Slack webhook to secure, dynamic notifications using lightweight middleware.

GitHub Webhooks Integration Automation Middleware Slack Cloudflare Workers

The Problem

A developer changes source code and pushes the changes to GitHub. Instead of team members repeatedly checking GitHub, we want GitHub to automatically notify a communication channel whenever code is pushed.

Developer Changes Code
Git Commit
Git Push
GitHub
Team Notification

The benefits of this approach include:

  • Immediate visibility
  • Reduced manual checking
  • Better team awareness
  • Event-driven communication
  • Reduced manual status updates

Can we do this without an integration platform?

Yes — for a basic notification.

Before We Build: Understand the Basics

1. URL / Endpoint An endpoint URL is an address where another application can send information. "A physical address tells a courier where to deliver a parcel. An endpoint tells an application where to deliver data."
2. Webhook A webhook allows one system to automatically notify another system when an event occurs. This is event-driven communication.
WITHOUT WEBHOOK:
Slack → "GitHub, anything new?" → GitHub

WITH WEBHOOK:
GitHub → "A push happened. Here is the information." → Slack
3. HTTP POST POST is the method GitHub uses to send the webhook information to another endpoint.
GitHub → HTTP POST → Webhook URL
4. JSON JSON is a structured data format applications use to exchange information. It uses a "key" to identify the data, and a "value" for the actual data. 
{
  "repository": "my-website",
  "branch": "main",
  "message": "Updated homepage"
}

  6. 6Set Content Type = application/json.

7. The Nested JSON Challenge

GitHub does send the information we need, but the webhook payload is more complex than simple key/value data.

Here is a SIMPLIFIED example of the data GitHub sends:

{
  "ref": "refs/heads/main",

  "repository": {
    "name": "my-website"
  },

  "pusher": {
    "name": "developer"
  },

  "commits": [
    {
      "id": "abc123",
      "message": "Updated homepage",
      "added": [],
      "modified": ["index.html"],
      "removed": []
    }
  ],

  "head_commit": {
    "message": "Updated homepage",
    "author": {
      "name": "Developer Name"
    }
  }
}

We can visualize this structure like this:

GitHub Payload
│
├── ref
│
├── repository
│     └── name
│
├── pusher
│     └── name
│
├── commits[]
│     └── commit
│           ├── id
│           ├── message
│           ├── added[]
│           ├── modified[]
│           └── removed[]
│
└── head_commit
      ├── message
      └── author
            └── name

This is nested JSON. Some values are inside other objects, while others are inside arrays.

For example, to get specific information we have to navigate deep into the structure:

  • repository.name
  • head_commit.author.name
  • commits[].modified[]

Slack Workflow webhook variables have limitations when directly consuming arbitrary nested structures like arrays and deeply nested objects.

The direct webhook was excellent for triggering the workflow, but it became restrictive when we wanted to extract, transform and aggregate richer GitHub data.

8. Do We Need a Large Integration Platform?

At this point, you might ask: "Do we now need Power Automate, Zapier, Make or another integration platform?"

Not necessarily.

We can introduce a lightweight middleware layer.

Middleware is a layer between two systems that receives information from one system, processes or transforms it, and sends the result to another system in a format it can understand.

9. Cloudflare Worker

For this project, Cloudflare Workers was used as lightweight serverless middleware.

The Worker gives us a public HTTPS endpoint where a small JavaScript function can receive GitHub's webhook, process the payload and forward a simpler payload to Slack.

13. Changed Files

Initially only "Added Files" was displayed.

When an existing file was modified, Slack displayed:

Added Files: None

That was technically correct but not useful because a file had actually changed. The solution was to process all three GitHub arrays:

  • added[]
  • modified[]
  • removed[]

The notification then became:

📂 Changed Files

➕ Added: ...
📝 Modified: ...
🗑️ Deleted: ...

This gives much better delivery visibility by showing exactly what happened to the codebase during the push.

14. Multiple Commits

One Git push does not always equal one Git commit.

Commit A
Commit B
Commit C
git push
ONE GitHub Push Event

GitHub provides a commits[] array of all commits in the push, and also a head_commit object.

head_commit represents the latest commit, but commits[] represents the commits included in the push payload.

Therefore the middleware was upgraded to iterate through commits[]. It generates:

  • commit count
  • commit summary
  • combined added files
  • combined modified files
  • combined deleted files

Example:

🔢 Commits: 3
💬 Commits:
• a12bc34 — Update homepage
• b23cd45 — Update navigation
• c34de56 — Update documentation

15. Aggregation & Deduplication

Commit A modifies:
index.html

Commit B modifies:
index.html

Commit C modifies:
styles.css

Without deduplication:

index.html, index.html, styles.css

The implementation uses JavaScript Set() to retain unique filenames.

Result:

index.html, styles.css

A JavaScript Set stores unique values, making it useful for removing duplicate filenames.

At this point the integration was functional and dynamic — but there was still an important question: How do we know that a request arriving at our public middleware endpoint really came from GitHub?

17. Keep Sensitive Values Out of Code

The Slack Workflow webhook URL should not be hard-coded into JavaScript source code.

Instead, it was stored in Cloudflare as a Secret: SLACK_WEBHOOK_URL

The Worker accesses it using: env.SLACK_WEBHOOK_URL

Worker Code
references
env.SLACK_WEBHOOK_URL
Cloudflare Secret
Actual Slack Webhook URL

Keeping secrets outside source code reduces the risk of exposing sensitive configuration through repositories, screenshots or shared code.

18. How Do We Know the Request Came From GitHub?

How do we know the request came from GitHub?

The Cloudflare Worker has a public HTTPS URL. If somebody discovers the endpoint, they could attempt to POST fake data to it.

Therefore the middleware must verify the sender.

19. GitHub Webhook Secret

A shared secret was configured in two places:

  1. GitHub Webhook configuration
  2. Cloudflare Worker secrets

We'll call this shared value: GITHUB_WEBHOOK_SECRET

GitHub uses the shared secret and the exact request body to generate an HMAC-SHA256 signature.

GitHub sends this calculated signature in a specific header:

X-Hub-Signature-256

22. Positive and Negative Testing

Scenario Expected Result Slack
Genuine signed GitHub push HTTP 200 / Accepted Notification ✅
Fake POST without signature HTTP 401 / Rejected No notification ❌
Fake POST with invalid signature HTTP 401 / Rejected No notification ❌

TEST 1 — Missing Signature

A fake POST was sent directly to the Worker.

It included: X-GitHub-Event: push

But DID NOT include: X-Hub-Signature-256

Worker result: "Missing GitHub signature." (HTTP 401)

Slack was NOT triggered.

TEST 2 — Invalid Signature

Another fake POST supplied an intentionally incorrect X-Hub-Signature-256 value.

The Worker independently calculated the expected signature. The values did not match.

Worker result: "Invalid GitHub signature." (HTTP 401)

Slack was NOT triggered.

TEST 3 — Positive Scenario

A genuine code change was committed and pushed to GitHub.

GitHub signed the request correctly. Cloudflare verified the signature.

The middleware processed the payload, and Slack received the formatted notification.

💡 Learning: Testing only the happy path is not enough. Security controls should also be deliberately tested with invalid requests.

23. Troubleshooting Model

When a complex integration fails, it's important to systematically isolate the problem.

1. Was a real file change made?
↓
2. Was a new Git commit created?
↓
3. Was the commit pushed to GitHub?
↓
4. Did GitHub create a webhook delivery?
↓
5. What HTTP response did the Worker return?
↓
6. Did signature verification succeed?
↓
7. Did Cloudflare call Slack?
↓
8. Did the Slack Workflow execute?
↓
9. Was the channel message generated?

Troubleshoot integrations from source to destination, one system boundary at a time.

27. What I Learned

Webhook

Event-driven communication between systems.

URL / Endpoint

The address applications use to communicate.

HTTP POST

A method used to send information to another endpoint.

JSON

Structured data exchanged between applications.

Nested JSON

Objects and arrays contained within other data structures.

Middleware

A processing layer between source and destination systems.

Payload Transformation

Converting one system's data into the structure required by another.

JSON Flattening

Converting nested values into simpler top-level variables.

Arrays

Used by GitHub to represent multiple commits/files.

Aggregation

Combining information across multiple commits.

Deduplication

Removing repeated values such as filenames.

Secrets

Keeping sensitive configuration outside source code.

HMAC-SHA256

Used here to verify that the webhook was signed using the shared secret.

Event Validation

Processing only expected GitHub events.

Positive Testing

Confirming valid requests work.

Negative Testing

Confirming invalid requests are rejected.

Troubleshooting

Tracing the integration one boundary at a time.
